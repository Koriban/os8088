# C64: a 1541 that is not a 1541 — `.D64`, read-only

**The decision this plans:** C64 gets `File > Attach disk image`, a `.D64`
mounts as device 8, and `LOAD"$",8`, `LOAD"NAME",8` and `LOAD"NAME",8,1`
work. **No drive CPU, no DOS ROM, no GCR.** The drive is a host-side reader
behind the KERNAL's own entry points.

It is written down before any code because the interesting part is not the
D64 walk - that is an afternoon - but **where the line is drawn**, and a line
drawn after the fact is a line drawn around whatever got built.

docs/C64-SPEC.md is the contract and this is the record of why it reads that
way. The port's own plan is `docs/plans/completed/C64-PORT-PLAN.md`; this is a
follow-up to it, not a wave of it.

---

## 1. What is already true, and it is more than it looks

**The serial bus is modelled, as EMPTY, and correctly** (C64-SPEC §6.2). CIA2's
PRA answers VICE's no-true-drive formula: bits 3-5 are ATN, CLK and DATA OUT,
bits 6-7 CLK and DATA IN, and **CLK IN and DATA IN read back as the inverse of
what this machine drives**. §11.3 records what the other answer costs - return
the raw register and DATA IN reads low, which is a device replying, and
`LOAD"*",8` waits for it for ever instead of timing out.

So today the machine asks, nothing answers, and the KERNAL gives up like a
real C64 with the drive switched off. **That is the behaviour this plan
replaces, and it is a working behaviour** - which means every step below can
be judged against it rather than against a blank screen.

`File > Smart attach` lands a `.PRG` in RAM and stops (`c64load.c`, `ovl_*`).
Autostart was wave 4 and never landed.

## 2. What this is NOT, pinned now

| | |
|---|---|
| a 1541 CPU | no 6502 in the drive, no 2KB drive RAM |
| a DOS ROM | **no second copyrighted sidecar.** `C64.ROM` stays the only one |
| GCR | no bit-level encoding, no head stepping, no rotation |
| writes | **read-only.** `SAVE` to device 8 refuses in words |
| fastloaders | see §6. Not reachable by THIS plan; §6.1/§6.3 cost the design that could, as separate work |
| `.D71` / `.D81` | §7 - cheap and not cheap, and not this plan |
| `.T64` / `.TAP` | no tape, unchanged (C64-SPEC §11.3) |

## 3. The format, which is the easy half

A `.D64` is 35 tracks, **683 sectors of 256 bytes = 174,848 bytes**. Sectors
per track is a four-step table - 21 for tracks 1-17, 19 for 18-24, 18 for
25-30, 17 for 31-35 - and the only arithmetic in the whole reader is turning
(track, sector) into a byte offset through it.

- **The BAM is 18/0.** Needed for the disk name and ID on the directory
  header line, and for the "blocks free" line. Not needed to read a file.
- **The directory is the chain from 18/1.** Each sector holds 8 entries of 32
  bytes; a sector's first two bytes are the link to the next (track 0 ends
  it, and then the second byte is the count of bytes used).
- **An entry** carries the file type at +2 (DEL/SEQ/PRG/USR/REL = 0..4, bit 7
  set means closed), the first track/sector at +3/+4, a 16-character name at
  +5 padded with `$A0`, and the block count at +30/+31.
- **A file is a sector chain** by the same link rule.

**Sizes other than 174,848 are refused by size before anything is parsed**:
the 40-track variants and the error-info forms exist, and a reader that
accepts a length it cannot address is the "Invalid Disk Image" the Apple II
plan already names. One number, one refusal, said in words.

## 4. Where it hooks, and the one thing that must be MEASURED

The C64's KERNAL reaches a device through vectored calls - `ILOAD` at `$0330`
and `ISAVE` at `$0332` for the whole operation, and the channel vectors
`IOPEN`/`ICLOSE`/`ICHKIN`/`IBASIN`/`IBSOUT` at `$031A`-`$0326` for the
byte-at-a-time path that `LOAD"$",8` and a BASIC `OPEN 2,8,2` take.

**THE ROM ADDRESSES ARE NOT WRITTEN IN THIS DOCUMENT AND MUST NOT BE.** The
port reads its KERNAL from `C64.ROM`, a committed sidecar; the trap points
are a property of THAT image and are pinned by locating them in it, once, in
a host-side tool, with the result checked into C64-SPEC as a measured table.
Inventing them here is how a plan and a branch stop agreeing - and this tree
already carries the lesson one project over (`os8088_false_premise_in_comment`):
a written-down claim stops being questioned.

**The trap is taken in `c64_rd_bx`'s existing slow path, not in the opcode
stream.** C64-SPEC §4.3 already routes `$D000-$DFFF` in an I/O bank out to
`c64_io_rd_bx`, and the fetch bias makes a PC compare cheap at the one place
the core already leaves the fast path. A trap tested per instruction would be
a tax on every program that never touches a disk; a trap tested where the
core already branches is not.

## 5. What gets built, in the order it is useful

Each story is useful alone and is judged on the glass.

### Story 1 — the reader, host-side, no emulation
`ovl_` code and a host test. Open a `.D64`, validate the length, walk the BAM
for name and ID, walk the directory, produce the entry list. **Verified by
`hosttest/`** - the port already has that harness shape (C64-SPEC §4.6) - with
a D64 the test WRITES itself, so a reader defect and an image defect cannot
cancel (the `os8088_sheet_format_gate` shape).

### Story 2 — `File > Attach disk image`, and the status line
The menu item ungreys. Attach validates and says what it mounted: name, ID,
and the entry count. Detach. **No KERNAL involvement yet** - this story is
provable with the machine sitting at the READY prompt, and it is where the
dialog's refusals get written.

### Story 3 — `LOAD"$",8`
The directory as a BASIC program, which is what a real drive sends: a line per
entry, link-and-line-number synthesised, the block count as the line number,
the name in quotes and the type after it. This is the first story where the
KERNAL is trapped, and it is the right first one because **the output is a
screenful of text that is either right or obviously wrong**.

### Story 4 — `LOAD"NAME",8` and `,8,1`
Secondary address 0 loads to the BASIC start; 1 loads to the file's own first
two bytes. The sector chain walk, into the RAM claim through
`c64_zzcopy_in` - the same far-to-far mover `c64load.c` already uses, so no
new mechanism. Wildcards (`*`, `?`) because `LOAD"*",8,1` is how half of all
software is started.

### Story 5 — the channel path, and the command channel
`OPEN 2,8,2,"NAME"` / `GET#` / `INPUT#` / `CLOSE`, and **channel 15**: the
error channel reading `00,OK,00,00` and `73,CBM DOS V2.6 1541,00,00`, plus
`U1`/`B-R` block reads. This is the story that reaches software doing its own
sector I/O without a drive CPU, and it is a real extension rather than a
nicety - see §6.

### Story 6 — the refusals, and they are a story
`SAVE` to 8, `OPEN` for write, `M-W`, and every DOS command that would change
the image, each refused **in words on the error channel** and in the status
row. A write that silently does nothing is worse than one that refuses.

## 6. The cheat, honestly

**The question asked was whether full drive emulation can be cheated. The
answer is: partly, and the part that cannot be is worth naming precisely.**

A fastloader does not use the KERNAL. It sends `M-W` commands that upload
6502 code into the drive's RAM, then `M-E` to execute it, and from that moment
the two machines talk over the serial lines in a private protocol with
bit-level timing. **There is no host-side interception of that**, because what
arrives is arbitrary code: the question "what does this loader want" is
answered by running it.

So the three cheats that exist, and what each is worth:

| cheat | what it buys | what it costs | verdict |
|---|---|---|---|
| **KERNAL traps** (§4) | every program that loads through LOAD/OPEN - all BASIC, a great deal of early software | ~2-3KB resident | **this plan** |
| **The command channel** (story 5) | software that does its own `U1`/`B-R` sector reads through channel 15 - loaders that are custom but not DRIVE-side | a few hundred bytes on top | **this plan, and it is the cheat worth having** |
| **A known-loader table** - recognise the uploaded code by checksum and substitute a host implementation | a finite list of titles | a table that is wrong the first time a loader is patched, and a maintenance burden with no end | **refused** |
| **One core, two contexts** (§6.1) - event-driven switching, the drive's clock ours, the disk a file | the loaders the three above cannot reach | a second 6502 context, a switch cost, and either a DOS ROM or §6.3's trap table | **a SECOND plan, not a refusal** |

**Story 5 is the cheat.** It is the one that extends reach without a drive
CPU, because block-level sector access is a DOS service, not drive code - the
drive's own ROM services `U1` and `B-R`, so a host that answers them is
answering as the DOS, not pretending to be the 6502.

### 6.1 One core, two contexts — NOT refused, and the first draft of this
### plan was wrong about why

**This section said the second machine was refused "on cycles", on the
ground that it meant a second 1 MHz 6502 running in LOCKSTEP with the first.
That is the expensive design and it is not the only one**, and the owner said
so. The two corrections are worth writing out, because both are properties of
being an emulator that a real pair of machines does not have.

**1. The switch is EVENT-DRIVEN, not per-cycle.** The two machines only
interact through four serial lines. So you run the C64 until it *touches the
bus* - a write to CIA2's PRA, or a read that would sample CLK/DATA IN - then
run the drive until *it* touches the bus or blocks on it, and swap back.
Between events neither can observe the other, so neither needs to be
scheduled. A fastloader's inner loop is the dense case and even that is a
transition every few instructions, not every cycle.

**2. The drive's clock is OURS, and the disk has no rotation.** Nothing
requires the drive to run at 1 MHz of wall time. The only invariant is the
RELATIVE ordering of the two machines at bus events - which is a shared cycle
counter, run-whichever-is-behind, and nothing more. And underneath that,
**the disk is a file**: head stepping, rotational latency and the GCR bit
stream are the drive's own fiction about a mechanism we do not have. A sector
that a real 1541 takes ~20 ms to bring under the head is a `c64_zzcopy_in`.
**So the emulated drive can be arbitrarily FASTER than a real one**, and the
loading that fastloaders exist to speed up is the part that costs nothing
here.

That turns the cost from "a second CPU in lockstep" - which is hopeless on a
4.77 MHz 8088 - into three bounded items:

| | |
|---|---|
| **the switch itself** | C64-SPEC §4.1 holds the whole 6510 in x86 registers, so there is no spare register for "which machine" and every swap is a full save and reload. Bounded and measurable: ~8 words each way, at a few hundred to a few thousand swaps per sector |
| **the drive's instructions** | a fastloader's drive-side loop is real 6502 that really executes. This is the honest cost and it is ADDITIVE to a port already measuring 0.54% of real speed on an XT |
| **the DOS ROM** | 16 KB, copyrighted, a SECOND sidecar beside `C64.ROM`. A policy cost, not a technical one - and §6.3 is how it might be avoided entirely |

None of those is a refusal. **It is a second plan, not a sentence in this
one** - and it wants this plan's command channel finished first, because that
is what gives it something to be measured against.

### 6.3 The hybrid, which is the shape worth trying

The attractive thing is that the two designs COMPOSE rather than compete.

- **The normal path stays host-side** (§4, §5): `LOAD`, the channel path,
  `U1`/`B-R`. No 6502, no ROM, no drive RAM.
- **An uploaded loader gets a real CPU.** `M-W` stores into an emulated 2 KB
  of drive RAM; `M-E` starts the second context there. The uploaded code runs
  against that RAM, the VIAs' serial lines, and - this is the trick - **the
  DOS ROM's documented entry points, TRAPPED and serviced from the host** the
  same way §4 traps the KERNAL, one machine down.

If that holds, **the DOS ROM is never needed as code, only as a table of
addresses**, and the second copyrighted sidecar disappears. §2's line moves
without being crossed.

**What still defeats it, stated so the next reader does not have to find
out:** a loader that drives the disk controller directly - reading GCR off the
VIA at `$1C01` and decoding it itself, rather than calling a DOS routine -
sees a mechanism that is not there. That class is real and it is exactly the
class most worth loading fast. The hybrid narrows the gap; it does not close
it, and a plan that claimed otherwise would be the "known-loader table" of
§6 wearing a better hat.

### 6.2 What a user sees when the cheat runs out
A fastloader uploads, executes, and the bus goes quiet. **The machine must say
so**, not hang: `M-E` with no drive to execute it is a refusal with a name,
on the error channel and the status row. That is the same argument §11.3
already won about `LOAD"*",8` timing out rather than waiting for ever.

## 7. `.D71` and `.D81`, priced now so the answer is not re-derived

- **`.D71`** - 70 tracks, two sides, 349,696 bytes. A 1571 on a C64 powers up
  in 1541 mode, so under this architecture it is **the same reader with a
  second sectors-per-track table and a doubled directory walk**. Cheap, and
  the right follow-up if anyone wants one.
- **`.D81`** - 80 tracks x 40 sectors, 819,200 bytes, and a DIFFERENT DOS:
  partitions, subdirectories, a different BAM across two sectors, and a
  command set this reader does not speak. **It is a second reader**, not a
  table, and it should be judged on its own rather than ridden in on this.

## 8. The budget

| | |
|---|---|
| C64 resident today | **42,774** (image 29,844 + bss 12,930), measured |
| the cap (SPEC.md §73) | 61,440 - **18,666 spare** |
| this plan, estimated | 2-3KB resident for the traps and the chain walk; the dialog, the validate and the directory format are `ovl_` |

Size is **not** the gate here, which is worth saying because it is the gate
on the Apple II's Disk II follow-up (APPLE2-SPEC §15.3) and the two are easy
to confuse. The gate here is the line in §2.

**MEASURE IT, DO NOT QUOTE IT.** The figure above was taken from the package
header - `image_unwrap`, then `+8` and `+10` - on the tree at the time of
writing, and the Apple II's own spec disagrees with a measurement of itself by
8.5KB right now, which is what that rule is for.

## 9. Verification

- **`hosttest/`** for the reader, against an image the test writes.
- **The glass** for every story: `LOAD"$",8` is a screenful of text, and
  `tests/glass.py`'s exact-cell reading is how a row asserts it rather than a
  photograph.
- **A negative control per story.** A directory listing that is right because
  the reader is right, and one that is right because the screen still holds
  the last one, look identical - so each row asserts against an image it
  chose, with a second image that must give a DIFFERENT answer.
- **The empty-bus behaviour must still pass with no image attached.** §1's
  timeout is a shipped behaviour and this plan must not break it; it is the
  one regression this work can cause and nothing else would catch it.
